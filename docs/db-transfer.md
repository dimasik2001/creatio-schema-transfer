# cst — перенос данных таблиц между стендами (режим «Database data»)

Статус (2026-11-22, не закоммичено): `db-tables` (п. 2.1), **CstGate** с сессиями (п. 1a) и **db-export / db-import /
db-inspect / db-restore** на шлюзе (п. 1b) сделаны и проверены на dev и между dev (MSSql) ↔ test (PostgreSQL), с
проверкой уникальных индексов (п. 1b.1); UI «Table data» (п. 1c) сделан и прогнан сценариями. Ответы пользователя — в п. 13.

## 1. Что и зачем

Новый режим cst собирает **бекап данных таблиц** стенда-источника (полный или частичный) и заливает его в
стенд-приёмник. Таблицы выбираются через пакеты: пользователь отмечает пакеты, cst находит в них объекты
(entity-схемы) и предлагает их данные. Из больших таблиц можно взять часть строк, при этом cst следит за
целостностью ссылок.

Принципы (решения пользователя 2026-11-22):
- **Только данные.** Таблицы и колонки на приёмнике создаёт Creatio (перенос схем/пакетов cst,
  UpdateDBStructure). cst пишет только строки.
- **Через HTTP, без строки подключения**: `Path` для режима не нужен.
- **Данные таблиц читаются и пишутся через CstGate** (решение 2026-11-22, заменило «только стандартные
  сервисы» для этого режима): свой пакет-шлюз с одной DLL, ставится на стенд только когда пользователь
  переносит данные таблиц. Всё остальное в cst по-прежнему идёт через стандартные сервисы. С cliogate не связан.
- **Нейтральный формат архива**: перенос MSSql ↔ PostgreSql работает.

## 1a. CstGate — SQL-шлюз

Пакет `CstGate` (UId `c57ca7e0-6a7e-4c57-9a7e-0000000c5747`, зависит от Base): **без схем**, только
`Files\Bin\CstGate.dll` (.NET Framework 4.7.2) и `Files\Bin\netstandard\CstGate.dll` (.NET-сборки Creatio). Исходник —
`gate/CstGate` (CreatioSDK 8.0.3 только для компиляции); cst собирает его при сборке и встраивает обе DLL как ресурсы,
пакет (gz/zip) собирает сам в момент установки — отдельных файлов возить не надо.

Почему так работает (декомпиляция 10.0.0.801): при старте приложения `SysWorkspace` загружает
`Files\Bin\<ИмяПакета>.dll` каждого пакета (`FeatureLoadPackagesBinAssembliesOnAppStart`), а `Global` регистрирует
`rest/<Сервис>` только из сборок с `[assembly: PackageReferenceAssembly(RefAssemblyMarker.ServiceRoutes)]`. Поэтому
имя DLL = имени пакета, атрибут обязателен, а после установки нужен **перезапуск приложения**.

Сервис `rest/CstGateService`, три POST-метода. Тело — JSON, можно gzip (определяется по сигнатуре, Content-Type
`application/octet-stream`); ответ — JSON, gzip при `"gzip": true` (cst всегда сжимает в обе стороны). Ошибки SQL
возвращаются в JSON (`ok: false`, текст, тип, номер ошибки СУБД, номер батча), не HTTP 500. Каждый вызов требует
операцию **CanManageSolution** (как cliogate). SQL идёт через собственное соединение Creatio (провайдер стенда:
Microsoft.Data.SqlClient / Npgsql — берётся из `DBExecutor.DBConnection`), поэтому не зависит от флагов
`DenySqlTextApiUsage`/`DenyCustomQueryApiUsage`. Своих таблиц/журналов в БД не создаёт; пишет строку в лог Creatio
(`CstGate`: пользователь, число строк, время, начало SQL).

| Метод | Запрос | Ответ |
|---|---|---|
| `Info` | `{}` | версия шлюза, runtime, пользователь, его ContactId (для политики `author`), canUse, движок, версия сервера, БД |
| `Query` | `{sql, params?, maxRows?, timeout?}` | `{columns:[{name,type}], rows:[[…]], truncated, ms}` — компактно: строки массивами, типы колонок один раз |
| `Execute` | `{batches:[{sql, params?, rows?} \| {load:{table, columns, rows, method?}}], transaction?=true, rollback?, isolation?, timeout?}` | `{affected:[…], results:[…] для батчей с rows:true, batchMs:[…], notes:[…], committed, ms}` |

- Типы значений: guid, string, int, long, decimal (строкой, без потери точности), double, bool, datetime (ISO без зоны),
  binary (base64), other.
- Параметры: `"p": значение` или `"p": {"type":"guid|datetime|binary|int|long|decimal|double|bool|string","value":…}`;
  в SQL — `@p`. Длинная строка на MSSql уходит как `nvarchar(max)`.
- **Запись пачками — батч `load`**: `{table, columns:[{name,type}], rows:[[…]]}` пишет строки в таблицу (обычно
  `#staging` той же транзакции, созданную предыдущим батчем). MSSql — `SqlBulkCopy` провайдера (берётся рядом с типом
  соединения, работает и с System.Data.SqlClient, и с Microsoft.Data.SqlClient; опции KeepNulls | CheckConstraints |
  TableLock), остальные движки — параметризованные многострочные INSERT (MSSql ≤ 2000 параметров, PG ≤ 30000).
  `OPENJSON` не подходит: у БД creatio-dev **compatibility level 110**, а `OPENJSON` требует 130 (типично для
  Creatio). Схема импорта: `CREATE TABLE #stg` → `load` → `INSERT … SELECT … FROM #stg WHERE NOT EXISTS` / `MERGE`
  → в одном вызове и одной транзакции.
- **Своё соединение без MARS**: шлюз открывает своё соединение того же провайдера из `DBExecutor.ConnectionString`
  с `MultipleActiveResultSets=false` (у Creatio MARS включён). С соединением Creatio `SqlBulkCopy` писал 20 000 строк
  за 4,5 с, со своим — за 0,17 с (вместе с этим исправлены флаги SqlBulkCopyOptions — какой вклад чей, не
  разделял); чтение 50 000 строк — 2,5 с → 1 с. Если строки подключения нет — шлюз берёт соединение Creatio и пишет об
  этом в `notes`.

### 1a.1 Проверено на creatio-dev (10.0.0.801, .NET Framework 4.8, MSSql 16, compat 110), 2026-11-22

- Установка: upload + InstallPackage 15 с, перезапуск (UnloadAppDomain), сервис отвечает через ~40 с; обновление
  версии (1.0.x → 1.0.y) тем же `gate-install` — ~36 с. Пакет лёг в `Pkg\CstGate\Files\Bin` (dev в FSM), в SysPackage
  `CstGate`, InstallType 1 — как cliogate.
- Первая версия без атрибута `PackageReferenceAssembly` не регистрировала сервис даже после перезапуска (404).
- Типы: guid, nvarchar с кириллицей, varbinary → base64, decimal(18,4) строкой без потерь, datetime ISO.
- Ошибки: `1/0` → «Divide by zero error encountered. [SqlException 8134]»; FK → полный текст + 547 + номер батча;
  несуществующая таблица → 208. Ошибка посреди чтения строк больше не ломает JSON (ответ пересобирается как ошибка).
- Dry run: INSERT 2 строк с `rollback` → affected 2, в таблице 0.
- Скорость чтения (`Query`, keyset-страницы): SysLocalizableValue 50 000 строк — ~1 с (23,6 МБ JSON → 6,6 МБ gzip);
  20 000 строк страницей `Id > @after` — 0,44 с. SysImage (347 строк, 23 МБ бинарных) — 2,5 с.
- Скорость записи (`gate-bench`: генерация → `#cst_stage` (load) → INSERT в UtkCstStatus, всё с ROLLBACK):
  20 000 строк — 0,97 с полный круг (load 165 мс, INSERT 389 мс); 100 000 строк — 6,7 с (load 0,7 с, INSERT 2,4 с,
  откат 3,1 с). Многострочные INSERT вместо bulk — 20 000 строк за 16 с (только как запасной путь для не-MSSql).
- Не проверено: .NET-сборка (netstandard) шлюза — нет стенда на .NET; PostgreSql (test недоступен); удаление пакета
  (`gate-uninstall` пока нет).
- `Execute` с `rollback: true` — **настоящий dry run**: всё выполняется в транзакции и откатывается, `affected`
  показывает, сколько строк вставилось бы/обновилось бы, ошибки FK/уникальных индексов ловятся на реальных данных.
- `rows: true` у батча возвращает его результат внутри той же транзакции (например, проверочный SELECT после INSERT).

Команды cst: `gate-status --env`, `gate-install --env [--force] [--no-restart]` (upload + InstallPackage → если
сервис не отвечает, перезапуск приложения и ожидание до 10 мин), `db-sql --env (--sql|--file) [--params-file]
[--max-rows] [--stats] [--execute [--rollback]]`, `gate-bench --env [--rows N] [--table Lookup] [--method bulk|insert]`
(замер записи, всегда с откатом).

### 1a.2 Сессии шлюза (v1.1.0)

Creatio не принимает запрос больше ~10 МБ на проводе (8,3 МБ gzip прошло, ~10 МБ — HTTP 400, предел WCF). Чтобы
большой импорт оставался одной транзакцией, у `Execute` есть сессия: `"session": "begin"` открывает своё соединение
с транзакцией и возвращает id, `"session": id` продолжает, `"end": "commit" | "rollback"` завершает. Ошибка в любом
батче откатывает всю сессию. Сессия привязана к пользователю, живёт только в этом экземпляре приложения и
откатывается после 15 минут простоя. `#staging`-таблицы живут всю сессию. Клиент (`GateSession`) сам режет слишком
большие `load`-батчи на несколько вызовов той же сессии (порог 7 МБ gzip).

## 1b. db-export / db-import / db-restore на CstGate (сделано 2026-11-22, проверено на dev)

Код: `src/Cst/Data/` — `DataPlan` (план), `DbCatalog` (`SqlDialect` + физические колонки через шлюз), `DataExporter`,
`DataArchive`, `DataImporter` (импорт и restore), `Gate` (клиент, сессии). Отличия от исходного проекта (п. 4–9):
- режим таблицы `where <SQL>` (условие на диалекте источника) вместо `filter` — через шлюз доступен обычный SQL;
- колонки берутся **физические** (INFORMATION_SCHEMA через шлюз, без identity/computed/rowversion), ссылки — из
  метаданных (RuntimeEntitySchemaRequest: lookup `X` ↔ колонка `XId`);
- права `Sys<T>Right` и переводы `Sys<T>Lcz` теперь читаются (через шлюз) и идут автоматически для каждой
  экспортируемой таблицы (`options: rights / translations`); их `RecordId` → T и `SysAdminUnitId`/`SysCultureId`
  имеют политику `drop` (строки с неизвестной ролью/культурой не пишутся);
- план без `tables:` = все объекты, созданные в `db packages:`, целиком (порог «большой таблицы» пока только в
  `db-tables` — сам план не режет молча).

**Экспорт**: строки по режиму (keyset-страницы по Id, `PageSize`), затем замыкание: для каждого ребра `pull`
дочитываются недостающие Id (`IN` пачками по 1000), пока ничего не прибавляется; `children:` берут дочерние строки
выбранных родителей. Ссылка, которая потянула бы больше `MaxPullRows` строк, останавливает экспорт с подсказкой.
Висячие ссылки источника (Id нет и на источнике) — предупреждение в manifest. Таблицы, подтянутые ссылками, но
не названные в плане, получают режим `pulled`.

**Импорт** (одна сессия = одна транзакция): `SELECT TOP 0 … INTO #cst_sN` (PG: `CREATE TEMP TABLE … AS … WITH NO
DATA`) — staging с типами приёмника → `load` (SqlBulkCopy) → политики (`author` = ContactId пользователя шлюза,
`null`, `drop`) → проверки `expect`/`pull` (Id нет ни на приёмнике, ни в архиве → exit 3, ничего не записано) →
по таблицам в порядке зависимостей: `#cst_nN` = новые Id, `INSERT … SELECT … JOIN #cst_nN`, в upsert — сначала
сохранить старые версии строк, потом `UPDATE … FROM`. Цикл ссылок разрывается на nullable-колонке: она пишется
NULL и ставится после всех вставок (self-reference, например `ParentId`, — так же). Колонки архива, которых нет на
приёмнике, пропускаются с предупреждением; обязательная колонка приёмника без значения по умолчанию, которой нет в
архиве, — ошибка. Перед COMMIT в work dir пишется `restore-db.json` (+ `<T>.updated.ndjson`).

**Restore**: одна сессия — отложенные колонки вставленных строк в NULL, удаление вставленных строк в обратном
порядке, старые версии обновлённых строк назад. Строки, удалённые каскадом FK на приёмнике, не возвращаются.

Проверено на creatio-dev (2026-11-22):
- `UtkCstSource`: экспорт 4 таблиц + `SysUtkCstStatusLcz` (переводы подхватились сами) за 0,9 с; dry run insert →
  0 новых, upsert → все обновлены.
- Круг: удалил 4 строки `UtkCstClient` → `db-import` вставил 4, контрольная сумма строк совпала с исходной →
  `db-restore` удалил их → повторный импорт вернул (сумма та же).
- Upsert: изменённая строка вернулась к значению из архива; `db-restore` вернул изменение; повторный upsert — исходные
  данные.
- Цикл `UtkCstClient.UtkLastOrderId` ↔ `UtkCstOrder.UtkClientId`: обе строки удалены и вставлены обратно,
  `UtkLastOrderId` поставлен после вставки заказа. Тестовые данные возвращены в исходное состояние.
- Частичный экспорт: `Account top 3` + `children: AccountAddress.Account` + `refs: Account.Type pull` → 3 Account,
  3 адреса, 3 AccountType (pulled), 12 строк SysAccountRight; `ParentId` отложен; dry run чистый.
- Подделанный архив (заказ ссылается на несуществующего клиента) → `MISSING … (pull): 1 ids`, exit 3, ничего не записано.
- Скорость: ConfActivityLog 60 837 строк — экспорт 2,7 с (архив 4,1 МБ), dry run insert 3,8 с, dry run upsert
  (с чтением старых версий для бекапа) 6,6 с.

### 1b.1 Проверено между dev (MSSql) и test (8.3.1, .NET Framework 4.8, PostgreSQL 18.1), 2026-11-22

- `gate-install --env test`: 6 с установка + перезапуск, отвечает через 37 с; провайдер Npgsql. Типы на PG: uuid,
  text с кириллицей, bytea → base64, numeric без потерь, timestamp, bool, int/bigint. Ошибки — с SQLSTATE (22012, 23505,
  42P01). Запись на PG (многострочные INSERT, не bulk): 20 000 строк — load 340 мс, полный круг 1,07 с.
- **Найдено и исправлено**: переводы `Sys<T>Lcz` у test свои (другие Id на ту же запись и культуру), импорт упал
  на уникальном индексе `IRC_UtkCstStatus` (RecordId, SysCultureId) и откатился. Теперь строки переводов
  сопоставляются по `(RecordId, SysCultureId)`, прав — по `(RecordId, SysAdminUnitId, Operation)`, а не по Id
  (upsert обновляет найденную строку приёмника, её Id не меняется).
- **Добавлена проверка уникальных индексов (п. 5.5)**: перед вставкой для каждого уникального индекса приёмника
  (кроме PK, без фильтра/выражений) считается, сколько новых строк уже имеют такие значения под другой строкой;
  по умолчанию импорт останавливается (exit 3, ничего не записано, примеры значений), `--on-unique skip` — такие строки
  не вставляются (отчёт SKIPPED).
- PG-ловушка учтена: отложенная колонка вставляется как `(CASE WHEN 1 = 0 THEN s.col END)` (голый NULL в SELECT на
  PG 10+ — text и не лезет в uuid).
- dev → test: dry run и импорт — 2 новых клиента, переводы сопоставились (4 строки, без дублей), значения строк на
  обоих стендах совпали до микросекунд; upsert обновил клиентов, статусы и переводы; два `db-restore` вернули test
  точно в исходное состояние (md5 строк клиентов и переводов совпали с исходными).
- test → dev: экспорт из PG (`db packages: UtkCstTarget`), импорт 1 нового клиента, значения совпали, `db-restore`
  вернул dev в исходное состояние.
- Account из dev на test (dry run): остановка на `Account.AccountLogoId → SysImage (expect)` — картинки на test нет;
  с `refs: - Account.AccountLogo pull` подтянулась строка SysImage (бинарная) и dry run прошёл (тип счёта, картинка,
  3 счёта, 3 адреса, 12 прав). Колонки, которых на test нет (Utk* в Account), пропущены с предупреждением. Реально на
  test не записывалось (только UtkCst* таблицы меняются в тестах).
- CstGate оставлен установленным на test (v1.1.0).

Не сделано / не проверено: UI (п. 10); .NET-сборка шлюза (оба стенда на .NET Framework); bulk COPY для PG (INSERT
и так быстрый); сброс кешей Creatio после импорта (только подсказка); `gate-uninstall`.

## 1c. UI «Table data / Дані таблиць» (сделано 2026-11-22)

Главное меню: Export · Import · Restore · **Table data** · Language · Quit (в сценариях Quit теперь = 5×Down,
Language = 4×Down; все `.keys` обновлены). Код: `src/Cst/Ui/DataFlows.cs`, `DataSources.cs`; тексты — с украинским
переводом. Подменю:
- **Export data**: стенд → проверка CstGate (нет или старая версия → объяснение и вопрос «Install/Update CstGate on X
  now?», по умолчанию No; установка перезапускает приложение) → Select (браузер пакетов: свои, Ctrl+A все, фильтр
  набором) или Load a plan → браузер таблиц (строки, ~размер, своя/заменённая; Space: skip → full → top → children)
  → итог: план в рамке и шаги Export archive / Save plan / Table mode (full, top N by …, where, ids, children, skip) /
  References (политика на колонку, «default») / Children (кто ссылается на выбранные) / Options (права, переводы) /
  Tables / Main menu. После экспорта — таблица результата и «Import it into a stand now».
- **Import data**: стенд → архив (недавние и `<папка настроек>\data\*.zip`) → состав архива → CstGate → insert/upsert →
  уникальные конфликты stop/skip → **dry run всегда** → таблица (в архиве / новых / обновлено / примечания) или
  проблемы → «Write into X?» (по умолчанию No) → запись, work dir запоминается.
- **Restore data**: стенд → только бекапы, сделанные **на этом стенде** → подтверждение → откат.

Файлы: планы — `<папка настроек>\plans\`, архивы — `data\`, work dir импорта — рядом с архивом; списки недавних — в
`cst.ui-state.json` (`RecentPlans`, `RecentDataArchives`, `RecentDataWorkDirs`).

**Найдено сценарием и исправлено**: `db-restore` не проверял, что бекап сделан на этом стенде. В сценарии Restore в
списке стендов первым стоял последний приёмник, `Down` выбрал dev вместо test, и restore удалил на dev две строки
UtkCstClient с теми же Id (их сразу вернул импорт исходного архива dev, контрольная сумма совпала). Теперь
`db-restore`/Restore data отказывается от чужого бекапа (`restore-db.json` → TargetUrl ≠ стенд, exit 2), а UI
показывает только бекапы выбранного стенда. Та же проверка добавлена в `restore` схем (`Transfer\Restorer`:
`restore.json` → `targetUrl`; чужой бекап → exit 2, бекап старого cst без `targetUrl` — предупреждение) и в список
Restore главного меню.

Сценарии (`tests\ui-scenarios`, прогнаны на dev/test): `data-export.keys` (браузеры, смена режима, Save plan, Export
archive), `data-import.keys` (dry run на dev, запись отклонена, Restore без бекапов), `data-import-write.keys` (запись
2 строк на test и Restore data — test вернулся к исходной сумме). Регресс: `lang-uk.keys`, `export-summary.keys`.
Для сценариев в настройках не должно быть недоступных стендов (bank из environments.json мешает: первый в списке).

## 2. Доступ к данным через стандартные сервисы (до решения о CstGate; остаётся для db-tables)

| Что | Как |
|---|---|
| Чтение строк | `DataService` SelectQuery по объекту (уже есть `CreatioClient.SelectAsync`), постранично |
| Метаданные объектов (колонки, lookup-ссылки, индексы) | метаданные entity-схем, которые cst уже выгружает (ExportSchema `.md` / runtime-схема) |
| Число строк | SelectQuery с агрегацией COUNT |
| Проверка «есть ли Id на приёмнике» | SelectQuery `Id IN (...)` пачками (как `Catalog.FindElementsAsync`, по 200) |
| Запись | временный SQL-скрипт `CstTmp_<hex>` в пакете приёмника → `InstallSqlScripts` → удаление скрипта; **тот же механизм, что у BindingSql** |

Почему запись через временный SQL, а не InsertQuery/UpdateQuery DataService:
- не срабатывают события объектов и бизнес-процессы (вставка 10 000 договоров не запустит 10 000 процессов);
- можно сохранить `Id`, `CreatedOn`, `CreatedById`, `ModifiedOn` как в источнике;
- быстрее: один скрипт пишет тысячи строк.

Следствия, которые надо учитывать:
- **Нужен пакет на приёмнике** для временных скриптов (любой редактируемый; выбирается в мастере, запоминается
  как маппинг). Скрипт удаляется сразу после выполнения, как сейчас у BindingSql.
- SQL генерируется **под движок приёмника** (`DbEngine` из конфига — как сейчас, без автоопределения).
  Oracle — не поддерживаем (как и BindingSql).
- Права: пользователь cst на источнике должен видеть все строки (DataService учитывает права на записи).
  Рекомендация — Supervisor или пользователь с «Чтение всех данных». Если у объекта права по записям,
  а у пользователя их нет — строки молча не придут: cst предупреждает, если объект администрируется по записям.
- Согласованного снимка нет: экспорт читает таблицы по очереди. Если стенд в работе, данные могут немного
  разойтись — предупреждение в итоге экспорта.
- Ошибка внутри скрипта приходит от `InstallSqlScripts` общим текстом («... CstTmp_... failed»). Поэтому
  **всё, что может уронить запись, проверяется до неё чтением** (п. 5.4, 5.5, 7.1), а скрипт пишет таблицу
  целиком в своей транзакции.

### 2.1 Результаты этапа 1 (creatio-dev, 10.0, MSSql, 2026-11-22; test 8.3 был недоступен)
1. **Бинарные колонки**: SelectQuery отдаёт их испорченными (байты как текст с заменой символов) — читать
   так нельзя. Работает GET `0/img/entity/hash/<Schema>/<Column>/<Id>` для **любой** бинарной колонки:
   SysImage.Data (549 б) и SysSettingsValue.BinaryValue (966 б) — SHA-256 совпали с эталоном. Также работает
   `rest/FileService/GetFile/<schemaUId>/<Id>`. Один запрос на ячейку — медленно для тысяч файлов, но надёжно.
2. **SecureText/HashText** (DataValueType 25/24) не переносятся, перечисляются в отчёте (сервис их не отдаёт).
3. **Переводы `<Table>Lcz`**: объектов для них нет (на 10.0 есть только `BaseLczEntity`, `*LczOld`,
   `SysPackageDataLcz`), DataService их не читает. В первой версии переводы не переносятся.
4. **Права на записи `Sys<X>Right`**: не объекты — DataService отвечает «not found». Найдено два пути
   (2026-11-22, подробно — п. 2.2).
5. **Постраничное чтение**: работают оба — `RowsOffset` + сортировка по Id и keyset (`Id > последний`,
   ComparisonType 7) в том же порядке. Берём keyset (не сдвигается при вставках).
6. **COUNT и размер одним запросом**: агрегат COUNT и `SUM(LENGTH(колонка))` (FunctionType 4 внутри
   AggregationType 2) работают и для текста, и для бинарных колонок (SysImage: 18 086 863 байт). Размер =
   SUM(LENGTH) переменных колонок (MSSql ×2 на символ) + фиксированные размеры остальных. Это ближе к
   правде, чем оценка по выборке.
7. **Метаданные**: `DataService/json/SyncReply/RuntimeEntitySchemaRequest {"Name"}` отдаёт isDBView,
   isVirtual, administratedByRecords и по колонкам: dataValueType, referenceSchemaName, isRequired, isVirtual,
   **isWeakReference** (= нет физического FK; так у CreatedBy/ModifiedBy), isCascade. Индексов там нет —
   уникальные индексы брать из `.md` схем (ExportSchema), этап 3.
8. **Временный SQL-скрипт**: тело ~1 МБ — save 7,7 с + install 4,6 с; ~5 МБ — 24 + 17 с; ~21 МБ — `SaveSchema`
   HTTP 400. Предел где-то между 5 и 21 МБ → `ScriptMb = 4`. Скорость ~300 строк/с при строке ~400 символов.
9. **InstallSqlScripts не оборачивает скрипт в транзакцию**: INSERT перед ошибкой остался в таблице.
   Каждый скрипт cst сам пишет `SET XACT_ABORT ON; BEGIN TRAN … COMMIT` (PG — скрипт и так одна транзакция,
   проверить на test).
10. **Текст ошибки скрипта доступен**: ответ сервиса общий («Installing following SQL scripts … failed»), но
    `SysPackageSqlScript.LastError` (читается DataService по UId скрипта) содержит настоящий текст
    (`THROW 50001, 'cst probe: custom error text'` → ровно этот текст). Это пригодится и BindingSql: вместо
    общей ошибки показывать LastError. Отсюда же «настоящий» dry run: скрипт пишет в транзакции, считает,
    делает ROLLBACK и `THROW` с итогом (до ~2000 символов) — cst читает итог из LastError.

### 2.2 Права на записи: два пути чтения (проверено на dev 2026-11-22)

Таблица `Sys<X>Right`: Id, RecordId, SysAdminUnitId, Operation (0 чтение, 1 изменение, 2 удаление),
RightLevel, Position, **SourceId** (откуда право: Author / Default / Manual — на dev 6/6/3 строк), CreatedOn…

**A. `rest/RightsService/GetRecordRights {"tableName":"SysAccountRight","recordId":"…"}`** — тот же вызов, что
делает окно «Права доступа». Отдаёт строки: Id, Operation, Position, RightLevel, SysAdminUnit (+ название).
- плюсы: стандартный сервис, экспорт остаётся только чтением, работает на любом стенде;
- минусы: **нет SourceId и дат**; один запрос на запись (~0,1–0,7 с; 10 000 записей — минуты); пустой ответ,
  если у записи нет прав.
- при записи SourceId придётся ставить фиксированный (Manual): права не будут пересчитываться как Default/Author.

**B. «Читатель через SQL-скрипт»** на источнике: временный скрипт-«почтовый ящик» `CstTmp_outbox` и скрипт-читатель
`CstTmp_reader`, который выполняет любой SELECT и пишет результат `FOR JSON` в Body ящика
(`UPDATE SysPackageSqlScript SET Body = CAST(CAST(@j COLLATE Latin1_General_100_CI_AS_SC_UTF8 AS varchar(max)) AS varbinary(max))`);
cst читает его через `SqlScriptSchemaDesignerService/GetSchema` → `body`. Проверено: все 15 строк SysAccountRight со
всеми колонками (включая SourceId), кириллица («Тест ї») цела. Канал через `LastError` для этого не годится:
колонка `nvarchar(500)` («String or binary data would be truncated»).
- плюсы: полные строки, пачками, один вызов на тысячи строк; тем же путём читаются **переводы `<X>Lcz`**,
  точные размеры таблиц, физические FK — всё, что DataService не отдаёт;
- минусы: **экспорт перестаёт быть только чтением** — на источнике нужен редактируемый пакет и право
  CanManageSolution, создаются и удаляются элементы (на FSM-стенде SaveSchema пишет и файлы в Pkg), скрипт напрямую
  пишет в системную таблицу `SysPackageSqlScript`; хранение Body (UTF-8 в varbinary) — недокументированная деталь,
  проверена только на 10.0/MSSql; для PostgreSql нужен свой вариант (`convert_to(…, 'UTF8')`).

Рекомендация: **A для прав по умолчанию** (стандартно, источник не меняется; SourceId → Manual с
предупреждением), **B — отдельной опцией** «расширенное чтение» (`--deep-read`), когда нужны переводы, SourceId
или скорость на больших объёмах. Решение — за пользователем.

## 3. Какие таблицы предлагать

### 3.1 Поиск по пакетам
1. Пакеты, выбранные пользователем (вкладка Packages текущего `SelectionBrowser`).
2. В них — `SysSchema` с `ManagerName = 'EntitySchemaManager'`.
3. Для каждой схемы берётся **корневой** объект (замещение указывает на ту же таблицу; колонки замещений
   входят в объект). Группы в списке:
   - **Own** — объект создан в выбранном пакете. Отмечен по умолчанию.
   - **Extended** — пакет только замещает чужой объект (например `Contact`). Не отмечен: это общая
     системная таблица, целиком её обычно не копируют.
4. Отбрасываются (с пометкой «почему»): представления (`IsDBView`), виртуальные объекты без таблицы.

### 3.2 Сопутствующие таблицы
- `Sys<Table>Right` — права на записи. **Переносятся по умолчанию** (решение пользователя) вместе с
  основной таблицей; строки с ролями/пользователями (`SysAdminUnit`), которых нет на приёмнике,
  пропускаются с подсчётом. Важно: запись через SQL не создаёт права для новых строк сама, поэтому без
  этих строк записи объекта с правами по записям на приёмнике никто не увидит — cst предупреждает.
- `<Table>Lcz` — переводы, если доступны через сервисы (п. 2.1, вопрос 3).
- Детали (`<Table>File`, дочерние объекты) — не сопутствующие; их предлагает шаг «дочерние записи» (п. 5.3).

### 3.3 Размер
Один SelectQuery на таблицу: COUNT + `SUM(LENGTH(...))` по текстовым и бинарным колонкам, плюс
фиксированные размеры остальных (Guid 16, дата 8 …) × число строк (проверено на этапе 1, п. 2.1). Индексы и
служебные страницы не учитываются, поэтому в UI — `~31 MB`.

Таблица считается **большой** при оценке **от 25 МБ** (решение пользователя) и по умолчанию получает режим
`top 1000 by CreatedOn desc` вместо `full`. Все пороги — в настройках (п. 3.4).

### 3.4 Настройки
Новый раздел `appsettings.json` (общий для всех стендов, с переопределением в env):

```jsonc
"DbData": {
  "LargeTableMb": 25,        // с какого объёма таблица «большая»
  "LargeTableRows": null,    // необязательный порог по числу строк
  "DefaultTop": 1000,        // сколько строк брать из большой таблицы по умолчанию
  "DefaultTopOrder": "CreatedOn desc",
  "MaxPullRows": 10000,      // предел подтягивания по одной ссылке (п. 5.2)
  "PageSize": 2000,          // строк в одной странице SelectQuery
  "ScriptRows": 1000,        // строк в одном временном SQL-скрипте (и не больше ScriptMb)
  "ScriptMb": 4
}
```

## 4. Режим таблицы

| Режим | Смысл |
|---|---|
| `full` | все строки |
| `skip` | не брать (ссылки на неё всё равно проверяются, п. 5) |
| `top N by <col> [asc\|desc]` | первые N по колонке (по умолчанию из настроек) |
| `filter <выражение>` | фильтр DataService: `CreatedOn >= 2026-11-01`, `Status.Code = 'Active'`, `and`/`or` — cst переводит в фильтры SelectQuery (своего SQL нет, мы ходим через сервисы) |
| `ids` | явный список Id (вставка из буфера / файла) |
| `children` | сами не выбираем, только строки, подтянутые ссылками (п. 5) |

Колонки — все колонки объекта (с учётом замещений), кроме вычисляемых/виртуальных и тех, что нельзя
прочитать (п. 2.1). Пропущенные колонки перечисляются в итоге экспорта и в manifest.

## 5. Целостность ссылок — главная часть

### 5.1 Граф ссылок
Только из **метаданных Creatio**: lookup-колонки объектов (ReferenceSchema), с учётом замещений.
Физических FK через сервисы не видно, но это и не нужно: на creatio-dev (2026-11-22) проверено, что
физических FK меньше, чем ссылок — 2169 FK против 2553 Guid-колонок `*Id` без FK (в том числе все
`CreatedById`/`ModifiedById`), так что метаданные — более полный источник. Ссылки, у которых на
приёмнике есть физический FK, упадут при записи — поэтому проверка до записи (п. 5.4) обязательна для всех.

Ребро: `Table.Column → RefTable(Id)`, флаги: обязательная колонка (NOT NULL), self-reference.

### 5.2 Замыкание (что ещё нужно взять)
Строки читаются в память/во временные файлы, поэтому ссылки собираются **локально** из прочитанных строк,
без лишних запросов:

```
выбрано[T] = строки по режиму T
повторять:
  для каждого ребра T.C → R:
    нужные = значения T.C в выбрано[T] (не NULL), которых ещё нет в выбрано[R]
    политика ребра:
      pull   → дочитать строки R по Id IN (нужные) пачками, выбрано[R] ∪= ...
      expect → запомнить: «должны быть на приёмнике» (проверка при импорте)
      author → только CreatedById/ModifiedById: если нет на приёмнике — пользователь импорта
      null   → если нет на приёмнике — NULL (только необязательные колонки)
      drop   → если нет на приёмнике — строку не вставлять
пока что-то добавилось
```

Политика по умолчанию:
- ссылка на таблицу **в выборке** (full/partial) → `pull`;
- ссылка на справочник/таблицу **вне выборки** (`Contact`, `SysAdminUnit`, `AccountType`, статусы) →
  `expect`: обычно они есть на приёмнике, а тащить пол-CRM не нужно;
- `CreatedById`/`ModifiedById` → `author` (решение пользователя: подставить контакт пользователя, под
  которым cst зашёл на приёмник; его Id cst читает при входе);
- self-reference (`ParentId`) и циклы → `pull`, иначе дерево рвётся.

Защита от взрыва: если `pull` по одному ребру добавляет больше `MaxPullRows` строк или затягивает объект
не из выбранных пакетов, замыкание останавливается, и UI показывает ребро-виновника
(«UtkPayment.ContactId → Contact: +48 213 строк») с выбором `expect` / `drop` / разрешить.

Полные (`full`) таблицы тоже участвуют: их исходящие ссылки проверяются так же.

### 5.3 Дочерние записи (обратное направление)
Для целостности они не нужны, но часто нужны по смыслу (договор без платежей бесполезен). На экране ссылок —
входящие рёбра в выбранные таблицы: `UtkPayment.ContractId → UtkContract`. Если отметить ребро, дочерняя
таблица получает режим `children` и берёт строки с `ContractId IN (выбранные договоры)`; затем снова
замыкание вперёд. По умолчанию выключено.

### 5.4 Проверка на приёмнике (при импорте, до записи)
Для каждого ребра с политикой `expect`/`author`/`null`/`drop` cst ищет Id, которых нет ни в архиве,
ни на приёмнике (SelectQuery `Id IN (...)`). Итог в предпросмотре:

```
UtkPayment.ContactId → Contact     12 ids missing on target   expect → BLOCKS import
UtkPayment.CreatedById → Contact    3 ids missing             author → import user
SysUtkContractRight.SysAdminUnitId  5 rows, unknown role      skip rows
```
Нарушение `expect` → импорт не начинается (код 3, отчёт `<archive>.missing-refs.md`), как сейчас с
отсутствующими зависимостями. Политику можно поменять прямо в мастере.

### 5.5 Уникальные индексы
Уникальные индексы берутся из метаданных объекта (Indexes с IsUnique). Строка с новым Id, но тем же
значением уникальной колонки, что на приёмнике (например, тот же `Code`), упадёт при вставке. Предпроверка
через SelectQuery по значениям уникальных колонок. Выбор, как у конфликтов bindings:
- **use target Id** — взять Id строки приёмника и заменить его во всех ссылках внутри архива;
- **skip** — не писать строку (и строки, которые на неё ссылаются с `pull`, — с отчётом);
- **abort**.

## 6. Архив

Отдельный тип архива (manifest `kind: "db-data"`, формат 3; старые cst откажутся его открывать):

```
manifest.json      источник (url, ядро, движок), время, пакеты, объекты: имя, UId схемы, режим,
                   колонки (имя, нейтральный тип, обязательная), пропущенные колонки и почему,
                   строк, sha256 файлов, рёбра с политиками, expect-ссылки
plan.txt           план выбора (п. 8) — можно открыть и повторить экспорт
data/<Table>/000001.ndjson.gz   строки пачками
```
Формат строк — типизированный NDJSON: guid, string, int, decimal (строкой), datetime (ISO, как хранит
Creatio), bool, binary (base64). Именно поэтому работает MSSql ↔ PostgreSql: SQL для записи строится уже
на приёмнике, под его движок.

## 7. Импорт

### 7.1 Проверки до записи (всё входит в dry run)
1. Вход на приёмник, `DbEngine` задан, выбран пакет для временных скриптов.
2. Каждый объект архива есть на приёмнике; каждая колонка архива есть у объекта приёмника (нет → ошибка
   или «пропустить колонку»); обязательная колонка приёмника, которой нет в архиве и у которой нет
   значения по умолчанию → ошибка.
3. Ссылки (п. 5.4), уникальные индексы (п. 5.5).
4. Порядок записи: топологическая сортировка по рёбрам. В циклах — вставка с NULL в «циклической» колонке
   и второй проход UPDATE (колонка должна быть необязательной, иначе ошибка с описанием цикла).

Dry run печатает план: по таблицам — сколько строк вставится, сколько обновится (upsert), сколько
пропустится и почему, сколько скриптов будет выполнено. Ничего не пишет.

### 7.2 Запись
Режимы (решение пользователя — без `replace`, на приёмнике ничего не удаляется):
- `insert` (по умолчанию) — только строки с новым Id, существующие не трогаем;
- `upsert` — новые вставить, существующие обновить по Id.

Скрипт на пачку строк (`ScriptRows` / `ScriptMb`) в своей транзакции:
- MSSql: `BEGIN TRAN` · `INSERT ... SELECT ... FROM (VALUES ...) WHERE NOT EXISTS` или `MERGE` · `COMMIT`;
- PostgreSql: `INSERT ... VALUES ... ON CONFLICT ("Id") DO NOTHING | DO UPDATE SET ...`.

Литералы строятся тем же кодом экранирования, что в BindingSql (два диалекта уже есть), бинарные —
`0x...` / `'\x...'::bytea`. Таблица без колонки `Id` — только `insert`, с предупреждением про дубли.

Атомарности на весь импорт нет (каждый скрипт — отдельный вызов). Если пачка упала: остановка, отчёт
«записано N из M пачек», предложение `restore`.

### 7.3 Бекап и restore
До записи cst читает с приёмника (DataService) текущие версии строк, которые будут обновлены (`upsert`),
и сохраняет их в work dir в формате архива; плюс список Id строк, которые будут вставлены. `restore`
(существующая команда, новый тип записи в `restore.json`) одним скриптом на таблицу удаляет вставленные
строки и возвращает старые версии — в обратном порядке записи.

### 7.4 После записи
Запись мимо ORM не сбрасывает кеши Creatio. cst сбрасывает то, что умеет сейчас (кеш системных
настроек — как после InstallData) и пишет в итоге: «если менялись справочники/права — сбросить Redis
или перезапустить приложение». Триггеры БД не отключаются.

## 9. CLI

```text
db-tables  --env <src> --packages "UtkCore,UtkContracts"   только чтение: объекты, строки, ~МБ, ссылки
db-export  --env <src> --plan <plan.txt> --out <data.zip>

           [--on-unique use-target|skip|abort] [--work-dir <dir>]
db-inspect --archive <data.zip>

```
Коды выхода — существующие: 1 конфиг/использование, 2 валидация (нет объекта/колонки, цикл с обязательной
колонкой), 3 отсутствующие ссылки, 4 запись не удалась, 10 прочее.

## 10. UI

Главное меню: новый пункт **Database data / Дані БД** → Export / Import.

**Export**
1. Стенд (любой).
2. Пакеты — существующая вкладка Packages (или «Load a plan»).
3. **Tables**: имя · пакет · группа (own/extended/companion) · строк · ~МБ · режим. Space — вкл/выкл,
   `M` — режим (full/top/filter/ids/skip). Большие (≥ `LargeTableMb`) подсвечены.
4. **References**: результат замыкания — по таблицам «выбрано N, подтянуто +M»; рёбра с политиками (Enter
   меняет); дочерние рёбра (вкл/выкл); красным — сработавший лимит.
5. Итог: Save plan / Export archive / Import сразу в другой стенд.

**Import**: стенд → архив → пакет для временных скриптов (запоминается для стенда) → предпросмотр
(объекты, колонки, ссылки, конфликты уникальных индексов с выбором) → режим insert/upsert → dry run
(всегда) → подтверждение (по умолчанию No) → прогресс по таблицам и пачкам → результат (Restore при ошибке).

Новые тексты UI — сразу с украинским переводом (`Lang.uk.cs`, проверка `tests\ui-lang-check.ps1`).

## 13. Решения пользователя (2026-11-22)

1. Только данные, без DDL.
2. Перенос между движками нужен → нейтральный формат.
3. Без строки подключения: только сервисы — чтение через DataService, запись через временный SQL-скрипт
   (как BindingSql). `Path` для режима не нужен.
4. Большая таблица — от 25 МБ; все пороги в настройках.
5. `CreatedById`/`ModifiedById`, которых нет на приёмнике → пользователь импорта.
6. Режима `replace` нет: только insert/upsert.
7. Права на записи (`Sys*Right`) переносятся по умолчанию, строки с чужими ролями пропускаются.
   **Открыто**: каким путём читать `Sys*Right` — A (RightsService, без SourceId) или B (SQL-читатель), п. 2.2.

Проверено `db-tables` на dev: `UtkCstSource` (4 таблицы, рёбра UtkCstClient ↔ UtkCstOrder = pull,
CreatedBy/ModifiedBy = author, no FK); `Utk_BX_NoDependencies,UtkYachtRental` — 136 таблиц, 412 ссылок, 14 с,
замещения (Account, Product…) не отмечены, бинарная `Account.Logo` и права по записям видны. Порог «large»
на реальной большой таблице ещё не проверялся.
